Access Model

Who can do what in Rental Property Manager today (single complex). Derived from backend/src/lib/access.js, middleware/auth.js, and the route files. Written 2026-10-11.

1. The roles at a glance

not signed in

Visitor

Browses the public site only.
  • Sees active, non-private properties
  • Sees site content, Things To Do, seasons
  • Cannot book (booking requires an account)
role: Guest

Guest / Renter

Self-signs up (email code). Public-site customer.
  • Requests bookings, sees own bookings
  • Downloads own booking document
  • Also sees private properties of any owner who invited them (an active grant)
  • Cannot enter the admin panel
role: Owner

Owner

Created by a SuperAdmin. Staff, but scoped.
  • Admin panel for only properties where ownerId = them
  • Their properties' bookings, seasons, add-ons, payment terms, documents
  • Their own invites, trusted renters and Gmail connection
  • Anything else returns 404 (not 403), so other owners' ids are never confirmed
role: SuperAdmin

SuperAdmin

The platform operator (you). Seeded.
  • Everything Owners can do, across all properties
  • Only role that manages users, site content and Things To Do
  • Sees unassigned properties (ownerId = null)
  • Can create invites on behalf of an owner

3. How scope flows: who owns what

Scope is a chain: User → Property (ownerId) → Booking (via its property). There is no "complex" level yet.

SuperAdmin — sees every node below, plus site content, Things To Do and all users
Owner A (User.role = Owner)
Property 1  ownerId = A
Seasons, add-ons, payment terms, rental agreement
Bookings → made by Guests; Owner A manages them
Property 2 (private)  isPrivate = true
Visible only to Guests holding an active OwnerGrant from Owner A
Owner A's invites, grants, Gmail connection
Owner B — same shape; cannot see or touch anything under Owner A (404)
Unassigned properties (ownerId = null) — SuperAdmin only
Global (no owner, no complex): Site content (homepage, brand, SEO, pages) lives on one shared default Site, and Things To Do is one table with no site or owner column.

4. Who sees which properties on the public site

Inactive

Hidden from everyone except those who manage it (Owner of it, SuperAdmin) in the admin panel. Looks identical to nonexistent on the public site.

Active + public

Everyone, including visitors.

Active + private

Its Owner, SuperAdmin, and Guests with an active (non-revoked) grant from that owner.

Admin-panel view

The public list is the same for everyone. Only the admin panel (sends X-Client header) switches staff to "everything I manage". The header picks the view; the role still decides authorization.

5. Account lifecycle rules

  1. Guests sign up themselves with an emailed 6-digit code.
  2. Owners are never self-service: a SuperAdmin creates them, and gets a one-time temporary password plus login URL to send manually.
  3. Created/reset accounts have mustChangePassword: the API blocks everything except changing the password (and public GETs) until done.
  4. isActive = false blocks sign-in and kills existing sessions on the next request.
  5. Sessions are a JWT in an httpOnly cookie; every request re-reads the user from the database, so role and deactivation changes apply immediately.
  6. Sign-in and last-seen timestamps are recorded and shown only to the SuperAdmin.

6. What multi-complex (option 2) would change

Today the only boundary between organisations is ownerId. A second complex would need a boundary above that, so owners of complex 2 can never see complex 1's data.

New level

Complex (Site) above Owner. Properties and Things To Do gain a siteId; the request domain resolves the Site.

New role

SiteAdmin: SuperAdmin powers (users, content, Things To Do) limited to one complex. Today's SuperAdmin becomes the platform operator over all complexes.

Decision to make

Can an Owner own properties in two complexes? And is a Guest account per complex or platform-wide? Both change how users and grants are keyed.

Main risk

Every existing query that uses propertyScope, bookingScope or global lists (users, Things To Do, content) must also filter by site. Missing one leaks data across complexes.
